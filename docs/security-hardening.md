# Security changes and compatibility

These changes address revoked sessions, account-switch data retention, resource abuse,
Content Security Policy and the transitive `uuid` advisory. System administrator selection
and owner/editor/viewer permissions are unchanged.

## Preserved contracts

- Same Firebase project, Auth accounts, Firestore database and `asia-east1/posRpc` callable.
- Same RPC methods, argument positions, `{ method, args, shopId }` envelope and successful responses.
  Rejections use the existing Firebase callable error channel (`unauthenticated` or `resource-exhausted`).
- Same shop, member, product, customer, order, capacity and device paths/fields.
  Order IDs, idempotency, monetary calculations and HMAC salt/hash formats are unchanged.
- Same IndexedDB draft/catalog keys and stored values; changing identity clears transient state
  and pending responses, without migrating saved drafts. Printer WSS frames remain unchanged.
- App Check adds the standard SDK verification header; no business payload fields are added.

## Current-session checks

Every recognized RPC queries the live Auth user before Firestore access. Deleted/disabled accounts,
removed Email verification, changed Email identity and `auth_time` older than the revocation
timestamp are rejected. Signature and expiration checks remain the callable SDK's responsibility.
Signing out, receiving an authentication rejection, or changing identity in another tab clears
rendered data and memory before reload. In-flight responses cannot cross identities.

## Abuse limits

Limits are per authenticated UID and shared across Functions instances using Firestore transactions.

| Operation | Limit |
| --- | --- |
| All recognized RPCs combined | 120 per 60 seconds |
| `initializeSession` + `registerDeviceSession` combined | 10 per 60 seconds |
| `generateDailyReport` + `getDemandStats` combined | 10 per 60 seconds |
| `createShop` | 5 attempts per rolling 24-hour window |
| Owned shops | 20, including existing shops |
| Device history | Latest 100 records |

Windows begin at the first request in an expired bucket. Rejected limit requests do not increment
the counters. Limits apply to all accounts, including system administrators; existing shops remain
readable/editable when their owner is already above the creation cap. Joining shops does not consume
the ownership quota. Each accepted RPC adds a live Auth lookup and a security-metadata transaction.

The only new document structure is `posSecurityLimits/{uid}`:

- `buckets`: fixed RPC/session/report/shop counters with millisecond `start` and integer `count`.
- `expiresAt`: Firestore timestamp, extended to two days after the latest accepted request.
- `shopRevision` / `deviceRevision`: transaction markers that serialize concurrent creations.

The TTL configuration is declared in `firestore.indexes.json`. TTL deletion is asynchronous and is
not used to decide whether a request is allowed. Shop/device limits query existing records inside
the same transaction as their marker, so TTL removal does not reset ownership or retention limits.
Existing device histories above 100 gradually shrink on new-device registrations; business records
are never removed by this cleanup. Firestore rules continue denying every direct client operation.

## CSP and dependency update

`build:web` regenerates Hosting CSP from fixed event-handler bodies. Dynamic values now live in
escaped `data-*` attributes, retaining the same handlers and UI actions. Arbitrary inline scripts,
unrecognized handlers, plugins and external framing are blocked. Inline CSS is retained for the
existing UI; HTTPS diagnostics and WSS connections remain available for configurable printers.
The two existing loopback Auth/Functions emulator endpoints remain allowed for local development.
Tests serve the same CSP as Hosting. Run `npm run build:web` whenever handler source changes.

Functions pins transitive `uuid` to patched CommonJS-compatible `11.1.1`. The installed consumers
use `v4()`; no application IDs are generated by this dependency. See
[GHSA-w5hq-g745-h8pq](https://github.com/advisories/GHSA-w5hq-g745-h8pq).

## App Check and production rollout

Web app `1:812259658073:web:cb279d4b7c99899513a448` has a reCAPTCHA Enterprise provider configured
with a one-hour token TTL and minimum score 0.5. The key permits `webpos-14776.web.app` and
`webpos-14776.firebaseapp.com`; domain verification is enabled. `runtime-config.js` contains
only public registration metadata. `SECURITY_HASH_SALT` remains a separate Secret Manager secret.

Registration alone does not deploy the application changes or enforce App Check on the existing
Function. Deploy in this order to avoid rejecting previously cached clients:

1. Build and publish Hosting with the updated client, CSP and runtime configuration.
2. Update/reload active installed PWAs and confirm the client obtains valid App Check tokens.
3. Deploy Firestore indexes/TTL and Functions. With `ENFORCE_APP_CHECK` unset or `true`, production
   enforcement is on; remove any explicit `false` override. Emulators always skip enforcement.
4. Confirm normal login/RPCs, denied missing-token requests, and App Check request metrics.

An explicit `ENFORCE_APP_CHECK=false` is available only for a deliberate temporary rollout/rollback;
it does not disable current-session, membership, rate or quota checks. Preview/custom domains need
their own appropriate App Check key/domain configuration before authenticated use.

Validation includes Node security tests, Chrome/WebKit workflows under CSP, and the isolated
Auth/Firestore/Functions emulator. The emulator covers concurrent rate/ownership limits,
device retention, revoked member reads/writes and existing order/payment/report contracts.
An isolated browser smoke check using the real registered provider obtained an App Check token
under the generated CSP without CSP violations; it did not authenticate a user or call a business RPC.
